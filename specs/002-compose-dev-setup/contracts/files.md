# Contract delta: files and names wtenv writes (spec 002)

**Feature**: `002-compose-dev-setup` | **Contract version**: 1 (additions only) | **Date**: 2026-10-10

This file lists only what spec 002 changes in
[001 contracts/files.md](../../001-worktree-runtime-isolation/contracts/files.md). Every format
not mentioned here is unchanged, byte for byte. In particular, the **Compose override file**
section of 001 still describes exactly what `up` generates in a worktree whose repository has no
override file of its own (FR-008).

## Names: one new row

| What | Name | Example |
|------|------|---------|
| Compose isolation file | `<worktree>/.wtenv/compose.isolation.yaml`, used only when the repository owns its override file; `.wtenv/` and the file are never symbolic links (FR-086, FR-009) | `/code/feature-x/.wtenv/compose.isolation.yaml` |

The rule about recorded names is extended by exactly this path. `down` and `gc` act on a
recorded override path only when its file name is one of the four override names **or** the
path is exactly `.wtenv/compose.isolation.yaml`. Any other path under `.wtenv/` is left alone
and reported under `failed`.

The repository's own override file is never in this table: wtenv never names, writes,
renames, deletes or excludes it (FR-002).

## Env file section

```text
# >>> wtenv managed (rewritten by `wtenv up`; do not edit) >>>
PORT=20000
WTENV_PORT_ADMINER_8080_TCP=20001
WTENV_PORT_BACKEND_8000_TCP=20002
WTENV_PORT_DB_5432_TCP=20003
WTENV_PORT_MAILPIT_1025_TCP=20004
WTENV_PORT_MAILPIT_8025_TCP=20005
WTENV_PORT_PLAYWRIGHT_9323_TCP=20006
WTENV_PORT_PROXY_80_TCP=20007
WTENV_PORT_PROXY_8080_TCP=20008
DATABASE_URL=postgresql://postgres:changethis@localhost:20003/app
# <<< wtenv managed <<<
```

- Lines inside, in this order (FR-013): the port variables of `ports`, in `ports` order; **then
  one variable per published port of the worktree's Compose setup**, sorted by service name,
  container port, then protocol, written only when `[compose]` is configured (FR-010, FR-016);
  then `DATABASE_URL` when a database is configured.
- Port variable name (FR-011): `WTENV_PORT_<SERVICE>_<CONTAINER PORT>_<PROTOCOL>`, where
  `<SERVICE>` is the compose service name in upper case with every character other than `A–Z`
  and `0–9` replaced by `_`, `<CONTAINER PORT>` is the container port in decimal, and
  `<PROTOCOL>` is `TCP` or `UDP`. The value is the host port assigned to that published port.
  A port tied to a `ports` variable (001:FR-031) has both variables, with the same number.
- With `[database] type = "compose"`, `DATABASE_URL` points at `localhost` and the database
  service's assigned host port (FR-019). This is a host-side value; a container that receives it
  through Compose interpolation gets the same host-side value (FR-025).
- Everything else in 001's section rules (markers, quoting, first and later writes, modes,
  symbolic links, `exec` reading the section) is unchanged.

## `.git/info/exclude` block

Unchanged rules. In the exec-only arrangement, the worktree's generated path is
`/.wtenv/compose.isolation.yaml` instead of the auto-loaded override name. The repository's own
override file is never added (FR-002). The block is shared by every worktree of the repository
and its lines are root-anchored, so a line added for worktree A (`/compose.override.yaml`) also
makes git ignore an untracked repository override of that name in worktree B; `up` in B warns
`compose_override_excluded` when it finds that ([cli.md](cli.md), step 5). git has no
per-worktree exclude file, so wtenv cannot avoid it. When `up` adopts a tracked file (FR-006), that file's
pattern is removed from the worktree's recorded `exclude_patterns`. Git ignores exclude rules
for tracked files, and `up` still only adds lines to the block (001), so the line stays until
the block is removed with the repository's last registered worktree.

## Compose isolation file

Generated by `up` in a worktree whose repository owns its override file. The layout is **exactly**
the 001 Compose override file layout: header line, `name:`, then for every service that publishes
ports `ports: !override` with one long-syntax entry per published port. Only where the entries
come from differs:

```yaml
# Generated by wtenv for this worktree. Do not edit or commit; `wtenv up` rewrites it.
name: "wtenv-feature-x-3f9a1c2b"
services:
  "adminer":
    ports: !override
      - {"target": 8080, "published": "20001", "protocol": "tcp", "mode": "ingress"}
  "backend":
    ports: !override
      - {"target": 8000, "published": "20002", "protocol": "tcp", "mode": "ingress"}
  "db":
    ports: !override
      - {"target": 5432, "published": "20003", "protocol": "tcp", "mode": "ingress"}
```

- The entries come from the **combined** model of the compose file and the repository's override
  (`docker compose -f <compose file> -f <repository override> --profile "*" config --format
  json`). A port that only the repository's override publishes is included. A fixed host port,
  or one taken from a variable, is replaced by the assigned port. `host_ip`, `protocol`, `mode`,
  `name` and `app_protocol` are repeated as Compose reported them (FR-003).
- `ports: !override` is required: a plain `ports:` list in a later file is appended to the
  repository override's list on Compose 2.24.4 and later (research R1, E1.2).
- The header line is the same as the override's, so the same header check protects it
  (001:FR-087).
- Compose loads this file only through `COMPOSE_FILE`, which `wtenv exec` and post-up commands set
  to three absolute paths in this order: the compose file, the repository's override, this file.
  They also set `COMPOSE_PATH_SEPARATOR=:` and `COMPOSE_ENV_FILES` ([cli.md](cli.md), `wtenv exec`). A plain
  `docker compose` in that worktree does not load it and is **not isolated** (FR-004).
- Written with mode `0644` through a temporary file and an atomic rename, like the override. A
  repeat `up` with nothing changed leaves identical bytes.
